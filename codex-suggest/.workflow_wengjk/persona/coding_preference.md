# Coding Preference

> 跨项目长期偏好。项目技术栈特有规则写入 `project_preference.md`。

## 组织与抽象

- 先复用已有模块、服务、工具、常量和项目模式，再考虑新增抽象。
- 只有新抽象能降低真实复杂度、消除有意义的重复或建立清晰边界时才引入。
- 单个入口内部的流程分段优先使用语义明确的私有方法。
- 单行或两三行、只调用一次且没有独立业务语义的逻辑优先内联。
- 入口方法负责清晰编排，复杂细节拆成可独立理解和验证的单元。

## 可读性

- 可读性优先于紧凑写法；复杂链式表达拆成命名明确的步骤、循环或私有方法。
- 尊重用户人工调整后的换行和布局，不做无关机械格式化。
- 过长参数、条件和调用按业务语义分行。
- 命名、日志、注释和文档使用直观、正式、贴近真实场景的表达，避免抽象黑话。

## 接口与模型

- 入口层只做参数接收、必要校验、业务分发和响应封装，不承载核心业务流程。
- Request/Response/DTO/VO 只保留当前契约实际需要的字段。
- 被多处引用或内部类名称明显影响可读性时，模型优先定义为独立类型。
- 服务端只返回客户端判断业务状态所需的数据，不为形式增加多余结构。
- 模型字段在语义一致时优先与实体字段保持一致。

## 校验与查询

- 前置条件在业务入口尽早校验，不满足时立即返回，避免无意义查询和写入。
- 上游已可靠校验的条件不在下游机械重复，除非入口不可控或链路风险高。
- 能一次确定全部冲突项时，优先完整反馈，不只返回第一条。
- 只判断存在性时优先使用 exists/count，不加载完整对象或大范围明细。
- 查询字段和数据范围保持为当前判断所需的最小集合。

## 数据与幂等

- 保存逻辑优先考虑并发、重试和幂等语义。
- 唯一键兜底且希望单条失败不影响整体时，优先逐条保存并处理重复异常。
- 能接受整批失败或底层明确支持 upsert 时再选择批量写入。
- 数据库已有可靠默认值或自动更新策略的字段，不在业务代码中重复赋值。
- 同一期需求的 SQL 变更优先集中维护，除非执行顺序、权限或交付方式要求拆分。
- 唯一索引命名优先使用 `uidx_` 加完整字段蛇形名称。

## 注释与测试

- 注释解释业务目的、前置条件、关键流程和不易从代码看出的原因。
- 不为简单赋值和自解释代码逐行添加注释。
- 语义仍准确的既有注释默认保留，不因重排代码顺手删除。
- 测试名称优先直接描述场景与预期；只有准备数据、模拟依赖或断言存在额外语义时补充注释。
- 交付前消除明显 warning、静态检查问题和可预见的边界错误。

## 条件式技术偏好

- Java/Spring 项目使用聚合查询 Request 时，项目采用 OpenAPI/Knife4j 的情况下优先使用 `@ParameterObject`。
- Java 项目使用 `record` 时，优先放在 DTO 或对应模型目录统一管理。
- 项目已有 Bean 拷贝工具时，字段名称和类型高度一致可优先复用；差异较多时显式组装。
- 项目已有代码生成器时，新表基础层代码优先按项目生成流程产生，再补业务方法、模型和测试。
- 跨任务、跨模块的重要技术约束可使用 `TODO_wengjk:` 或 `TASK_wengjk:` 标记，并在工作流决策中同步留痕。
