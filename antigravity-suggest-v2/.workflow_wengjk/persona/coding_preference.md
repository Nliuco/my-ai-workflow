# Coding Preference

> 长期个人主档，只保留跨项目通用的编码偏好。

## 服务层组织

- 优先少建没有明确归属的新 Service。
- 逻辑能自然归到已有聚合 Service 或领域 Service 时，优先复用。
- 只是单个接口内部的流程分段时，优先用当前类的私有方法表达。
- 只有明显跨多个场景复用、或单类已经难以维护时，才新增横向 Service。

## 聚合接口写法

- 入口方法保持清晰的流程编排。
- 复杂细节拆成语义明确的私有方法。
- 可读性优先于紧凑写法；复杂 Stream 链应拆成命名清晰的中间步骤、普通循环或语义明确的私有方法，避免在判断条件中堆叠流式表达式。
- 比起过度抽象，更偏好“入口 + 私有方法 + 复用现有服务”。
- 单行且只调用一次的逻辑，通常直接写在调用处。
- 仅调用一次、只有两三行且不承载独立业务语义的简单转换逻辑，优先直接内联在调用处；不要只为把 Stream lambda 换成方法引用而拆出大概率不会复用的私有方法。

## 模型组织与契约

- Request 契约保持精简，不保留当前业务流程不会读取或使用的字段。
- 会被业务层、测试或其他调用方多处引用的请求模型，优先定义为独立类，不使用静态内部类增加引用成本。
- 即使模型只有一处调用，只要 `外部类名.静态内部类名` 过长、明显影响代码简洁性和阅读体验，也优先拆成独立类。

## Controller

- Controller 只做参数接收、调用 Service、封装响应。
- 如果前置条件已由上游保证，Controller 不要堆太多兼容分支。
- 使用 Request 对象封装聚合查询参数时，优先添加 `@ParameterObject`，让 Knife4j/Swagger 清晰展示各查询字段。

## 前置校验与判空

- 入口前置条件优先在业务入口前快速校验。
- 喜好判空操作用 Optional 处理，一些代码喜欢用流处理。
- 不符合条件直接抛出业务异常，不继续做无意义查询或写入。
- 批量校验能够一次性确定全部冲突项时，优先完整反馈所有问题，不只返回遇到的第一条错误。

## 默认字段与数据库

- 创建 PO 对象时，对有数据库默认值或更新策略的字段（如 `createTime`、`updateTime`、`isDelete`），优先依赖数据库，不在业务代码里重复赋值。
- 只有业务语义需要显式覆盖时，才在代码里设置。

## 工具复用与复制

- 已有工具或常量能表达语义时，优先复用。
- PO、Request、DTO、VO 间字段名称和类型完全一致，且占绝大多数时，优先使用项目封装的 `BeanUtils.copyProperties` 完成复制，再单独设置差异字段。
- 字段名称或类型不一致较多时，直接显式组装对象。

## 注释规范

- 注释优先解释业务目的、前置条件和关键流程。
- 单元测试优先通过 `@DisplayName` 或等价机制用中文说明测试场景与预期结果。
- 既有准确注释默认保留，不因代码重排顺手删除。
- 跨任务重要技术约束，使用 `TODO_wengjk:`、`TASK_wengjk:` 或 `COMMENT_wengjk:` 高亮标记。
