# Coding Preference

> 跨项目、跨语言长期主档。技术栈特有规则放入 `languages/`，项目特有规则放入 `project_preference.md`。

## 组织与抽象

- 优先少建没有明确归属的新模块或 Service。
- 逻辑能自然归到已有聚合边界、领域边界或模块时，优先复用。
- 单个入口内部的流程分段优先使用当前类型的私有方法表达。
- 只有明显跨多个场景复用、单文件已难维护或能建立稳定边界时，才新增横向抽象。
- 比起过度抽象，更偏好“清晰入口 + 语义私有方法 + 复用现有能力”。
- 单行或两三行、只调用一次且不承载独立业务语义的逻辑优先内联。
- 不只为把匿名函数换成方法引用而拆出大概率不会复用的方法。

## 流程与可读性

- 入口方法保持清晰的业务流程编排。
- 复杂细节拆成语义明确、可独立理解和验证的步骤。
- 可读性优先于紧凑写法；复杂链式表达拆成命名明确的中间步骤、普通循环或私有方法。
- 判断条件中避免堆叠难以阅读的流式表达式。
- 尊重用户人工调整后的换行和代码布局，不做无关机械格式化。
- 方法调用、参数列表和条件表达式过长时按业务语义分行。

## 接口与模型

- 入口层只做参数接收、必要校验、业务调用和响应封装，不承载核心业务流程。
- Request 契约保持精简，不保留当前流程不会读取的字段。
- 被业务层、测试或其他调用方多处引用的模型优先定义为独立类型。
- 即使只调用一次，只要内部类型名称明显影响阅读，也优先拆成独立类型。
- 服务端只返回调用方判断业务状态所需的数据，不为形式新增多余结构。
- 模型字段在语义一致且不冲突时优先与实体或领域字段保持一致。

## 校验边界

- 前置条件在业务入口尽早校验，不满足时立即返回，避免无意义查询和写入。
- 上游已可靠校验的条件不在下游机械重复，除非入口不可控或链路风险高。
- 校验字段和约束服务于真实业务边界，不保留冗余防御式判断。
- 能一次性确定全部冲突项时，优先完整反馈所有问题，而不是只返回第一条。

## 查询与数据范围

- 只需要判断存在性时优先使用 exists/count，不加载完整对象或大范围明细。
- 查询字段和数据范围保持为当前业务判断所需的最小集合。
- 避免为了复用方便读取无关数据或在内存中做本可由数据源完成的过滤。

## 保存、并发与幂等

- 数据保存优先考虑并发、重试、部分失败和幂等语义。
- 唯一键兜底且希望单条失败不影响整体时，优先逐条保存并处理重复异常。
- 能接受整批失败或底层明确支持 upsert 时，再选择批量写入。
- 数据库已有可靠默认值或自动更新策略的字段，不在业务代码中重复赋值。
- 只有业务语义需要覆盖默认行为时才显式设置。

## SQL 与数据变更

- 同一期需求的 SQL 变更优先集中维护，除非执行顺序、权限或交付方式要求拆分。
- 唯一索引命名优先使用 `uidx_` 加完整字段蛇形名称。
- 数据修复和迁移必须说明影响范围、幂等方式、回滚或补偿手段。

## 工具复用

- 已有工具、常量和基础设施能表达语义时优先复用。
- 避免在业务类型中重复定义基础常量。
- 模型字段名称和类型高度一致时可使用项目已有复制工具，再单独设置差异字段。
- 字段差异较多时显式组装对象，不为少量可复制字段引入额外工具。
- 项目已有生成器时，基础样板代码优先使用项目生成流程，再补业务逻辑和测试。

## 注释

- 注释解释业务目的、前置条件、关键流程和不容易从代码中看出的原因。
- 长方法可用简短注释分段，帮助快速理解完整流程。
- 不为简单字段赋值或代码已经直接表达清楚的内容逐行添加注释。
- 语义仍准确的既有注释默认保留，不因代码重排或增加分组顺手删除。
- 只有逻辑变化导致注释失真、明显重复或用户明确要求时才调整。
- 跨任务、跨模块的重要技术约束可使用 `TODO_wengjk:` 或 `TASK_wengjk:` 标记，并在工作流决策中同步留痕。

## 测试与交付

- 测试名称直接描述业务场景与预期结果。
- 只有准备数据、模拟依赖或断言存在额外语义时补充简短注释。
- 验证范围随风险和影响面扩大；窄改动做最小验证，共享链路和高风险流程扩大回归。
- 交付前尽量消除 warning、静态检查问题和可预见的边界错误。

## 命名与表达

- 日志、注释、文档和命名使用贴近真实场景的正式表述。
- 优先使用直观业务词，不滥用抽象黑话。
- 接口路径优先简短、可读，避免无意义拼接。
