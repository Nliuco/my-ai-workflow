# Coding Preference

> 长期主档，只保留跨项目通用的编码偏好。

## 服务层组织

- 优先少建没有明确归属的新 Service。
- 逻辑能自然归到已有聚合 Service 或领域 Service 时，优先复用。
- 只是单个接口内部的流程分段时，优先用当前类的私有方法表达。
- 只有明显跨多个场景复用、或单类已经难以维护时，才新增横向 Service。

## 聚合接口写法

- 入口方法保持清晰的流程编排。
- 复杂细节拆成语义明确的私有方法。
- 可读性优先于紧凑写法；复杂 Stream 链应拆成命名清晰的中间步骤、普通循环或语义明确的私有方法，避免在判断条件中堆叠流式表达式。
- 比起过度抽象，更偏好“入口 + 私有方法 + 复用现有服务”。
- 单行且只调用一次的逻辑，通常直接写在调用处。
- 仅调用一次、只有两三行且不承载独立业务语义的简单转换逻辑，优先直接内联在调用处；不要只为把 Stream lambda 换成方法引用而拆出大概率不会复用的私有方法。

## 模型组织与契约

- Request 契约保持精简，不保留当前业务流程不会读取或使用的字段。
- 会被业务层、测试或其他调用方多处引用的请求模型，优先定义为独立类，不使用静态内部类增加引用成本。
- 即使模型只有一处调用，只要 `外部类名.静态内部类名` 过长、明显影响代码简洁性和阅读体验，也优先拆成独立类；是否拆分类不只由复用次数决定。

## Controller

- Controller 只做参数接收、调用 Service、封装响应。
- 如果前置条件已由上游保证，Controller 不要堆太多兼容分支。
- 使用 Request 对象封装聚合查询参数时，优先添加 `@ParameterObject`，让 Knife4j 清晰展示各查询字段。

## 前置校验

- 入口前置条件优先在业务入口前快速校验。
- 不符合条件直接返回业务异常，不继续做无意义查询或写入。
- 批量校验能够一次性确定全部冲突项时，优先完整反馈所有问题，不只返回遇到的第一条错误。

## VO 与返回

- 服务端只返回客户端判断业务状态所需的数据。
- 如果客户端已有明确 UI 展示，不要为了形式新增多余返回结构。
- `record` 类型优先放在 DTO 或其子目录里统一管理。

## 常量与字段

- 与单个 PO 字段强相关的少量状态，优先放到对应 PO 类里。
- 业务级配置放活动常量类或模块常量类。
- 两态字段不必为了形式创建枚举，简单常量更轻。

## SQL 变更组织

- 同一期需求在未归档前，相关 SQL 变更优先合并维护在同一个 SQL 文件里。
- 除非执行顺序、权限边界或交付方式明确要求拆分，否则不倾向为同一期需求新增多个零散 SQL 文件。
- 唯一索引命名统一使用 `uidx_` 前缀加字段名全称，按索引字段顺序用蛇形命名拼接，例如 `uidx_source_type_source_id`。

## 默认字段赋值

- 创建 PO 对象时，`createTime`、`updateTime`、`isDelete` 这类建表已有默认值或更新策略的字段，默认不在业务代码里手动赋值，优先依赖数据库默认值。
- 对有数据库默认值或更新策略的字段，优先依赖数据库，不在业务代码里重复赋值。
- 只有业务语义需要显式覆盖时，才在代码里设置。

## 批量保存与幂等

- 少量数据保存时，优先考虑并发幂等语义。
- 依赖唯一键兜底且希望单条失败不影响整体时，优先逐条保存并捕获重复异常。
- 能接受整批失败或底层已支持 upsert 时，再考虑批量写入。
- 交付前尽量消除明显 warning、黄线和可预见的静态检查问题。

## 校验边界

- Controller 已校验过的参数，Service 内一般不重复兜底。
- 除非入口外部不可控或链路风险高，否则不要为了防御式编程重复检查。
- 请求校验字段和注解应服务于真实业务边界，不保留当前业务流程不需要的冗余校验。

## 查询边界

- 业务只需要判断数据是否存在时，优先使用 `exists`、`count` 等存在性查询，不加载完整业务对象或大范围明细后再在内存判断。
- 查询字段和数据范围以当前业务判断所需的最小集合为准，避免为了复用方便读取无关数据。

## 工具复用

- 已有工具或常量能表达语义时，优先复用。
- 避免在业务类里重复定义基础常量。
- PO、Request、DTO、VO 间字段名称和类型完全一致，且这类字段占绝大多数时，优先使用项目封装的 `BeanUtils.copyProperties` 完成复制，再单独设置少量差异字段。
- 字段名称或类型不一致的情况较多时，直接显式组装对象。

## 注释

- 注释优先解释业务目的、前置条件和关键流程。
- 长方法可以用简短注释分段，帮助快速阅读。
- 聚合 Service 的业务入口应参考实际业务流转，在关键步骤前说明该段代码的职责。
- 不为简单字段赋值或代码已经直接表达清楚的内容逐行添加注释。
- 单元测试和集成测试应优先通过 `@DisplayName` 用中文说明测试场景与预期结果。
- 语义仍然准确的既有注释默认保留，不因代码重排、增加分组或调整结构而顺手删除。
- 只有逻辑变化导致注释失真、注释明显重复或用户明确要求时，才调整或删除原有注释。
- 跨任务、跨模块且后续实现必须遵守的重要技术约束，应在代码中使用 `TODO_wengjk:` 或 `TASK_wengjk:` 高亮标记，并在工作流决策文件中同步留痕。

## 格式与可读性

- 尊重用户人工调整后的换行和代码布局。
- 方法调用、参数列表和条件表达式过长时，优先按业务语义分行。

## 命名与表达

- 日志、注释、文档使用贴近真实业务场景的正式表述。
- 优先使用直观业务词，不滥用抽象黑话。
- Request、Response、DTO、VO 等 POJO 类字段命名，在不冲突且语义一致时，优先与对应实体字段名保持一致。
- 接口路径优先使用简短、可读的业务命名。
